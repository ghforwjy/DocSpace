# EasyDocs 文档版本管理 API 测试场景设计

## 1. 测试范围概述

本测试方案旨在全面覆盖 EasyDocs 文档版本管理 API 的所有功能点，包括：

- 版本信息获取
- 版本合并
- 版本恢复
- 编辑历史记录
- 版本差异比较
- 版本注释更新

## 2. API 列表

| API 路径 | 方法 | 功能描述 |
|---------|------|---------|
| `/api/2.0/files/file/{fileId}/history` | GET | 获取文件所有版本列表 |
| `/api/2.0/files/file/{fileId}/history` | PUT | 合并版本历史 |
| `/api/2.0/files/file/{fileId}/edit/history` | GET | 获取编辑历史记录 |
| `/api/2.0/files/file/{fileId}/edit/diff` | GET | 获取版本差异 URL |
| `/api/2.0/files/file/{fileId}/restoreversion` | POST | 恢复到指定版本 |
| `/api/2.0/files/file/{fileId}/comment` | PUT | 更新版本注释 |
| `/api/2.0/files/file/{fileId}` | GET | 获取文件信息（可指定版本） |
| `/api/2.0/files/file/{fileId}/log` | GET | 获取文件操作历史 |

## 3. 测试场景设计

### 场景 1: 获取文件版本列表

**目标**: 验证能够正确获取文件的所有历史版本

**前置条件**: 
1. 用户已登录
2. 目标文件存在且有多个历史版本

**测试步骤**:
1. 创建一个新文件
2. 多次修改文件内容以创建多个版本
3. 调用 `GET /api/2.0/files/file/{fileId}/history`
4. 验证返回的版本列表完整性

**预期结果**:
- 返回状态码 200
- 版本数量与实际创建的版本数一致
- 版本按时间倒序排列
- 每个版本包含完整信息：Version, VersionGroup, Title, 等

**边界条件**:
- 文件只有 1 个版本
- 文件有大量版本（10+）
- 文件不存在 → 404
- 无权限访问 → 403

---

### 场景 2: 合并版本历史

**目标**: 验证版本合并功能正常工作

**前置条件**:
1. 用户已登录且有编辑权限
2. 文件有多个版本

**测试步骤**:
1. 创建文件并添加 3 个版本（v1, v2, v3）
2. 调用 `PUT /api/2.0/files/file/{fileId}/history`，参数 `version=2, continueVersion=true`
3. 获取更新后的版本列表
4. 验证版本组（VersionGroup）的变化

**预期结果**:
- 返回状态码 200
- v2 和 v3 的 VersionGroup 应该相同（被合并）
- v1 的 VersionGroup 保持不变

**边界条件**:
- 合并最早的版本（version=1）
- 合并最新的版本（version=latest）
- 参数 `continueVersion=false`（恢复到该版本）
- 版本号不存在 → 错误处理

---

### 场景 3: 恢复到指定版本

**目标**: 验证版本恢复功能

**前置条件**:
1. 用户已登录且有编辑权限
2. 文件有多个版本

**测试步骤**:
1. 创建文件，初始内容 = "v1 content"
2. 修改内容为 "v2 content" → v2
3. 修改内容为 "v3 content" → v3
4. 调用恢复 API，恢复到 v2
5. 验证文件内容已恢复

**预期结果**:
- 返回状态码 200
- 当前文件内容为 "v2 content"
- 创建新的版本 v4（基于 v2）
- 编辑历史正确记录恢复操作

**边界条件**:
- 恢复到当前版本
- 恢复到不存在的版本号
- 无权限编辑 → 403

---

### 场景 4: 获取编辑历史

**目标**: 验证编辑历史记录功能

**前置条件**:
1. 用户已登录
2. 文件有多次编辑记录

**测试步骤**:
1. 多次编辑文件，每次由不同用户编辑
2. 调用 `GET /api/2.0/files/file/{fileId}/edit/history`
3. 验证历史记录完整性

**预期结果**:
- 返回状态码 200
- 每条记录包含：版本号、修改时间、修改人、修改内容描述
- 记录按时间倒序排列

**边界条件**:
- 无编辑历史（新文件）
- 匿名访问（该 API 无需认证）

---

### 场景 5: 获取版本差异 URL

**目标**: 验证版本差异比较功能

**前置条件**:
1. 用户已登录
2. 文件有多个版本

**测试步骤**:
1. 创建文件 v1，内容 = "Hello"
2. 修改为 "Hello World" → v2
3. 调用差异 API，获取 v1 和 v2 的比较 URL
4. 验证 URL 有效性

**预期结果**:
- 返回状态码 200
- 返回有效的差异查看 URL
- URL 中包含版本信息

**边界条件**:
- 只有一个版本（无法比较）
- 匿名访问（该 API 无需认证）

---

### 场景 6: 更新版本注释

**目标**: 验证版本注释功能

**前置条件**:
1. 用户已登录且有编辑权限
2. 文件有多个版本

**测试步骤**:
1. 获取文件的某个版本
2. 调用 `PUT /api/2.0/files/file/{fileId}/comment`，添加注释
3. 验证注释已保存

**预期结果**:
- 返回状态码 200
- 该版本的注释字段已更新
- 其他版本的注释不受影响

**边界条件**:
- 注释为空
- 注释超长
- 无权限编辑 → 403

---

### 场景 7: 获取指定版本的文件信息

**目标**: 验证按版本号获取文件信息

**前置条件**:
1. 用户已登录
2. 文件有多个版本

**测试步骤**:
1. 创建文件 v1，标题 = "Document v1"
2. 修改标题为 "Document v2" → v2
3. 调用 `GET /api/2.0/files/file/{fileId}?version=1`
4. 验证返回的信息对应 v1

**预期结果**:
- 返回状态码 200
- 文件标题为 "Document v1"
- 版本号为 1

**边界条件**:
- 版本号不存在 → 404
- 不指定 version 参数 → 返回最新版本

---

### 场景 8: 获取文件操作历史

**目标**: 验证文件操作日志功能

**前置条件**:
1. 用户已登录
2. 文件有多次操作记录

**测试步骤**:
1. 对文件进行多种操作：创建、编辑、重命名、分享
2. 调用 `GET /api/2.0/files/file/{fileId}/log`
3. 验证日志完整性

**预期结果**:
- 返回状态码 200
- 日志包含所有操作记录
- 每条记录包含操作类型、时间、操作用户

**边界条件**:
- 无操作历史
- 指定日期范围查询
- 分页查询（startIndex, count）

---

### 场景 9: 版本号和版本组规则验证

**目标**: 验证版本号和版本组的递增/合并规则

**前置条件**:
1. 用户已登录
2. 理解版本管理逻辑

**测试步骤**:
1. 创建新文件 → v1, VersionGroup=1
2. 正常保存 → v2, VersionGroup=2
3. 再次保存 → v3, VersionGroup=3
4. 合并版本（从 v2 开始）→ v3 的 VersionGroup 应该变为 2
5. 验证规则

**预期结果**:
- 正常保存时 Version 和 VersionGroup 同时递增
- 合并后，指定版本及后续版本的 VersionGroup 相同
- 版本号始终唯一且递增

---

### 场景 10: 权限验证

**目标**: 验证各 API 的权限控制

**测试矩阵**:

| API | 匿名用户 | 只读用户 | 编辑用户 | 所有者 |
|-----|---------|---------|---------|-------|
| GET /history | ✅ | ✅ | ✅ | ✅ |
| GET /edit/history | ✅ | ✅ | ✅ | ✅ |
| GET /edit/diff | ✅ | ✅ | ✅ | ✅ |
| GET /file (with version) | ✅ | ✅ | ✅ | ✅ |
| GET /log | ❌ 403 | ✅ | ✅ | ✅ |
| PUT /history | ❌ 403 | ❌ 403 | ✅ | ✅ |
| POST /restoreversion | ❌ 403 | ❌ 403 | ✅ | ✅ |
| PUT /comment | ❌ 403 | ❌ 403 | ✅ | ✅ |

## 4. 非功能性测试

### 4.1 性能测试
- 大量版本文件的查询响应时间
- 并发访问版本历史的稳定性

### 4.2 兼容性测试
- 不同文件类型（docx, xlsx, pptx, pdf, 等）的版本管理

## 5. 测试数据准备

### 测试用户
- Owner（所有者）
- Editor（编辑者）
- Viewer（查看者）
- Anonymous（匿名用户）

### 测试文件
- 新建文件（无版本历史）
- 单版本文件
- 多版本文件（3-5 个版本）
- 已合并版本的文件
- 不同类型的文件

## 6. 测试执行顺序

1. 基础功能测试（场景 1, 4, 7）
2. 版本操作测试（场景 2, 3, 6）
3. 高级功能测试（场景 5, 8, 9）
4. 权限验证测试（场景 10）
5. 非功能性测试
